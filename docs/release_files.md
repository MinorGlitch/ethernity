# Release files

This page gives repository-local release verification instructions. The complete release procedure
lives in the wiki:

- [Wiki: Release files](https://github.com/MinorGlitch/ethernity/wiki/Release-Artifacts)

## Files in each release

For each published binary variant, expect:

- the archive itself, a `.zip` or `.tar.gz` file
- a CycloneDX software bill of materials, or SBOM, generated by scanning that exact archive,
  `*.sbom.cdx.json`
- a separate Sigstore signature bundle for each archive and SBOM, `*.sigstore.json`

Each release also includes `ethernity-source-vX.Y.Z.tar.gz` plus its SBOM and Sigstore bundle.
That tagged source archive is built after injecting the generated recovery-kit bundles and includes
the frozen extension test PDFs used by the Homebrew formula. Homebrew must use this
release archive rather than GitHub's automatically generated tag archive.

Starting with 1.2, native archives cover Apple silicon macOS, Linux x64 and ARM64, and Windows
x64. Native Intel Mac archives and Homebrew bottles are no longer built. Intel Mac users can
use the [Python installation route](install.md#python-users), which is not tested on Intel macOS
in CI. Previously published release assets remain unchanged.

Releases also include the verified Python wheel, version-bound `install.sh` and `install.ps1`,
and `SHA256SUMS`. Stable three-part versions include `MinorGlitch.Ethernity.yaml` for WinGet.
Each of these files has a Sigstore bundle. SHA256SUMS covers every unsigned payload except
itself. Direct installers always check the archive checksum and can additionally require
Sigstore verification. See [installation](install.md).

Verify each Sigstore bundle before using its archive.

Packages include the template fonts and their license notices. PDFs embed subsets of those fonts;
users do not need to install matching system fonts to view or print them.

Packages also include the local assets for `ethernity --web`. Browser mode uses the same app as
the terminal launcher and needs no extra downloads. Native package smoke checks open a real
browser session over its WebSocket and verify that disconnecting stops its app process.

SBOMs are platform-specific. The release workflow scans each final archive with the
repository-pinned Anchore SBOM action and Syft version. It does not reuse a dependency manifest as
the SBOM for multiple release files.

## Release authorization

A release tag must resolve to a commit on `origin/master`, and that exact commit must have a
successful `push` run of `ci.yml` on `master`. Pull-request and manually dispatched CI runs do not
qualify a commit for release. A manually initiated release must dispatch the release job from
`master`. The job resolves the tag again immediately before publication and stops if it moved.

Required repository settings:

- protect `v*` tags against updates and deletion
- enable immutable GitHub Releases
- configure the `release` environment without required reviewers or self-approval restrictions
- restrict deployment branches/tags for that environment to the release policy

Each platform job builds, smoke-tests, and packages its binaries without release credentials.
The release does not apply Developer ID signing, macOS notarization, or Windows Authenticode
signing. No Apple or Windows signing certificates are required.

The `release` environment publishes the files and creates keyless Sigstore signatures using the
GitHub Actions job identity. These signatures verify the archives and their SBOMs; they do not
sign the executables for macOS or Windows. Each `.sigstore.json` bundle contains the data needed
to verify its file. The release does not publish separate `.sig` and `.pem` files.

The `signatures` job uploads these bundles as `release-signatures`. The `release` job downloads
them with the archives and SBOMs before publication.

Publication starts as a draft and never overwrites files. Retrying a failed publication job
byte-compares existing files with the saved build artifacts and uploads only missing files to the
draft. A fresh run for an already-published release downloads and verifies every signature instead
of rebuilding the release. Missing, unexpected, or mismatched files stop publication. The job publishes the release only after the exact archive, SBOM, and
Sigstore-bundle set is present. A partial published release is treated as an integrity failure, not
repaired in place.

## Python and Windows package channels

The source job builds one wheel from the same source archive used by Homebrew, verifies its
contents, installs it with the locked dependencies, and runs the packaged recovery smoke test.
CI and release publication reuse that wheel. After a stable, non-draft GitHub release is
published, the PyPI job downloads and verifies the source archive and wheel from that release.
It restores the source archive's standard Python filename and publishes the same bytes with
`uv publish --trusted-publishing always`. It does not rebuild them. Upload retries use uv's
existing-file checks rather than overwriting distributions.

Before the first publication, configure a PyPI trusted publisher on `ethernity-paper`:

- GitHub owner: `MinorGlitch`
- Repository: `ethernity`
- Workflow: `pyinstaller.yml`
- Environment: `release`

No PyPI API token is used. Missing publisher configuration fails the publication job; it must
not be treated as a successful release to all channels. Homebrew dispatch and PyPI publication
are independent, visible downstream jobs and can be retried after GitHub publication.

The WinGet manifest refers to the existing Windows x64 ZIP and its SHA-256 checksum. CI tests
installation, upgrade, command resolution, and removal on Windows using that same ZIP. It
also checks upgrades from a small previous-version fixture so stale files cannot hide a bad
replacement. Submit the manifest to `microsoft/winget-pkgs` after the corresponding stable
archive is public. Community acceptance is a separate step; do not advertise the WinGet command
before acceptance. No additional Windows executable build or signing certificate is required.

Before announcing a stable release, check that GitHub, PyPI, and Homebrew all offer that version,
then update installation notes in the README and wiki. Remove the 1.2 pre-release installation
notice when publishing 1.2. WinGet may lag while its submission is reviewed; document that state.

## Homebrew release requirements

Homebrew publication consumes only an already-published stable `vX.Y.Z` source release. It stages
one formula, validates that exact formula on Apple silicon macOS and Linux x64, and assembles
the two bottles before updating the tap. Builders receive no tap credential. The
`homebrew-production` environment is restricted to `master` and `v*` and is the only job allowed
to read `HOMEBREW_TAP_TOKEN`. It has no required reviewers or self-approval restrictions.

The formula generator resolves Python resources from the release's `uv.lock`, including their
SHA-256 checksums. It selects compatible wheels for each platform and uses the locked source
archive when no matching wheel exists or a wheel cannot be relocated by Homebrew.
On macOS, `cbor2` is built from source because its wheels lack space for Homebrew to rewrite
the library path. Other compatible wheels remain in use. Selection checks the CPython version and ABI,
architecture, and minimum platform version: macOS 13 or glibc 2.35. These wheel limits do not
extend the operating systems covered by the bottle tests. Shared and universal wheels are reused
where applicable; Apple silicon macOS and Linux x64 have separate bottles and tests.

`HOMEBREW_TAP_REPO` is the configured GitHub repository name, for example
`MinorGlitch/homebrew-tap`. The workflow derives the Homebrew tap name, `MinorGlitch/tap`, from
it. Bottle releases start as drafts. The workflow checks that every expected file is present and
there are no extras, then publishes the release before pushing the validated formula with a
normal fast-forward update. Enable immutable releases on the tap repository as well as the source
repository. Existing release files are reused only after a byte-for-byte match and are never
replaced.

The binary release explicitly dispatches the Homebrew workflow after stable publication.
A GitHub release event created with `GITHUB_TOKEN` does not start another workflow. Dispatch uses
`actions: write` in a separate job, without granting that permission to builders.

Each bottle release also stores the validated formula and `publication.json`, which records the
source commit, original tap base, and file checksums. A fresh retry reuses those files. The original
bottle tag stays fixed while the formula push checks the current tap base separately. Retries can
finish a failed formula push, but cannot downgrade a newer formula or overwrite changed assets.

## CI and packaging rehearsal

Linux, macOS, and Windows each run the unit, integration, rendering, and UI suites in four
concurrent jobs: two balanced UI groups, PDF rendering tests, and unit/integration tests. The
groups do not overlap. Linux collects branch coverage in all four jobs; a separate job combines
the results and enforces the application (85%) and document inspector (45%) gates without
rerunning tests. Browser, visual, portability, compatibility, and audit gates remain separate.
The responsive PDF matrix and terminal snapshot suite run concurrently. Only rendering jobs
install Poppler, and only core jobs install Node dependencies and download printed-kit references.
The minimum-Python Linux portability check keeps its full selection and uses two pytest workers.

The kit verification job uses the official Playwright container, pinned by version and digest,
with its browsers and system libraries already installed. Keep that image aligned with the
Playwright version in `kit/package-lock.json`. The job still verifies the generated bundle files,
runs the Node tests, and checks both kit variants in Chromium and WebKit. It does not download
browser dependencies through apt or raise the job's 20-minute limit.

`native-packages.yml` builds the same four native archives for CI and releases. On pull requests,
documentation-only changes skip native builds. `homebrew-build.yml` runs the same formula audit,
source install, test, and bottle build on both Homebrew platforms. Pull requests run it when
packaging, dependency, workflow, script, or packaged-resource files change. Master push, scheduled,
and manual CI runs perform the full packaging rehearsal. None of these CI builds publish files.

Homebrew installs locked wheels together and keeps the source-build toolchain only on targets
that need source resources. macOS still builds `cbor2` from source for bottle relocation. Each
platform checks source recovery, bottle installation and recovery, reinstall, and uninstall.
An additional upgrade check installs a minimal version `0.0.1` fixture through Homebrew, upgrades
it to the actual release bottle, verifies the active version and removal of its obsolete command,
runs the release formula's recovery test, and uninstalls it. This exercises Homebrew's upgrade
mechanism; it does not run a previous Ethernity release or replace format-compatibility tests.

Only downloaded archives and Homebrew's Ruby tooling are cached. Ethernity's installed files and
bottles are rebuilt on every run. Ruby cache keys include the platform, architecture, Homebrew
revision, Ruby version and gem lockfile; download keys also track the locked resources. Cached
archives still undergo Homebrew's checksum validation.

`python-packages.yml` builds the source archive and builds, checks, and installs a wheel from it
for both CI and releases. CI stages the Homebrew formula in that same job, so bottle checks can
start when the source is ready without waiting for native archives or WinGet. The rehearsal uses
that exact source artifact with the formula's normal URL and checksum. Release signing waits for
both Python and native package verification. This checks installation before the public release
exists.

Python commands use `UV_LOCKED=true`; setup rejects an outdated `uv.lock`. Source and wheel builds
use the locked build dependencies without a second, unpinned build environment. Kit and packaging
artifacts remain available for 30 days so failed jobs can be retried with the same files.
Workflow syntax is checked with a pinned, checksum-verified actionlint binary.

The native matrix and asset inventory live in `tooling/release/inventory.py`. Shared publication
code validates exact file sets, handles draft retries, and refuses replacements. Its tests exercise
failed uploads, moved tags, stale tap branches, prereleases, and completed-release retries.

## Linux binary baseline

Both Linux architectures build and smoke-test on Ubuntu 22.04. The package job checks every bundled
ELF file and rejects requirements newer than glibc 2.35. Ubuntu 22.04 is the tested minimum; this is
not a promise that every distribution with the same glibc version has all required system libraries.
The native smoke test restores a frozen root and update using the packaged executable.
Linux x64, Linux ARM64, and Windows x64 also run installer lifecycle checks using the real
built archive: install, rejection of damaged and invalid replacements, upgrade, reinstall, and
uninstall. Windows additionally checks migration from the old installer layout. The Windows
installer retries atomic directory renames for up to ten seconds when Windows reports access
or sharing conflicts. A failed replacement restores the previous installation and PATH. If
rollback itself fails, the previous files are kept in the reported staging directory. Integration
tests exercise both temporary and persistent directory locks with real Windows file handles.
Homebrew's separate Apple silicon macOS and Linux x64 jobs install, reinstall, test, and remove their
bottles after the existing source build and recovery test.

## Extension compatibility checks

For releases that include v1.2 extensions, CI must pass these frozen checks:

- `uv run pytest tests/e2e/test_end_to_end_v1_2_extension_golden.py -v`
- `cd kit && node --test tests/v1_2_extension_frozen_e2e.test.mjs`
- `cd kit && node build_kit.mjs`
- `cd kit && node --test tests/loader_html.test.mjs`
- `cd kit && npm run test:browser`

The default `recovery_kit.bundle.html` and `recovery_kit.scanner.bundle.html` files use gzip around
a Roadroller-packed application. Roadroller is a build dependency; opening a kit needs no network.
`kit/lib/pack_kit.mjs` keeps separate, fixed packing parameters for the lean and scanner variants.
Both use eleven contexts and a 64 MiB model budget. The decoder runs in a disposable worker;
each build verifies that it reproduces the complete application before publishing a bundle.
To retune after substantial application changes, run Roadroller's CLI with
`-O2 -M64 -Sx11 -D -t text -a write` on the exact HTML passed to `packKitHtml`. Compare the final
gzip size, printed QR count, memory use, and browser startup time before saving the selected
parameters. Ordinary builds use those saved parameters without an optimizer search.

The generated `recovery_kit.assembler.html` template is also packaged for printing the two startup
codes. All three resources are rebuilt from `kit/`; the assembler template is not a standalone
recovery app.
Optional Brotli builds use suffixed `*.brotli.bundle.html` names and never replace the default
gzip files. Gzip builds use the pinned `@gfx/zopfli` npm development dependency with 100
iterations and verify the decompressed output before publishing it. No separate compressor
executable is needed. The compressor runs only during the build and is not included in the kit.
Variable names use a fixed minifier sequence to reduce the compressed size.

Python wheels and PyInstaller distributions embed only the two default gzip bundles. Optional
Brotli files remain standalone build outputs under `kit/dist/`.

Rendered documents are validated with the bundled PDFium library through `pypdfium2`.
PyInstaller distributions must include that native library and both PDFium version files.
Homebrew installs the locked platform wheel so page validation works without a system PDF viewer.

Wheels and PyInstaller distributions must also include `resources/designs/_shared/*.json`.
The built-in A5 layouts use these files together with each design's `design.json` and `style.json`.

The generated default bundles must support extensions and pass the Chromium and WebKit tests for
local-file loading and recovery worker execution before release. Offline browser recovery kit
bundles are generated during the release build.

The local `scripts/build_pyinstaller.sh` and `scripts/build_pyinstaller.ps1` wrappers run `npm ci`,
generate both default gzip bundles, reject missing or extra packaged HTML bundles, and then run
PyInstaller. They require a Node.js version supported by [kit/package.json](../kit/package.json)
and npm.

`pyproject.toml` owns the packaged bundle inventory. The build backend, local wrappers, CI,
and release jobs share `tooling/release_resources.py` to check that inventory and the minimum
bundle size. The source archive includes this verifier so building from a release uses the same
checks. Run it from the project root:

```sh
python -m tooling.release_resources --kit-directory src/ethernity/resources/kit
python -m tooling.release_resources dist/*.whl dist/*.tar.gz
```

## Verification example

```sh
tag=v1.2.0
file="ethernity-${tag}-linux-x64.tar.gz"
cosign verify-blob \
  --certificate-identity "https://github.com/MinorGlitch/ethernity/.github/workflows/pyinstaller.yml@refs/tags/${tag}" \
  --certificate-oidc-issuer "https://token.actions.githubusercontent.com" \
  --bundle "${file}.sigstore.json" \
  "$file"
```

Use the archive and bundle from the same tag and variant. For a release created by manually
dispatching the workflow from master, use this exact certificate identity instead:
`https://github.com/MinorGlitch/ethernity/.github/workflows/pyinstaller.yml@refs/heads/master`.
Keep the issuer check in both cases. Apply the same command to the SBOM and its bundle.
The signing job verifies each new signature against its own workflow identity before upload.

Python prereleases such as `v1.2.0rc1`, `v1.3.0b1`, and `v1.3.0.dev1` are always marked as
prereleases. Manual dispatch can also mark a final version as a prerelease. Homebrew publication
accepts only published stable tags of the form `vX.Y.Z`.

## Do not run an unverified download

Do not run the binary yet if any of these are true:

- the archive name does not match your OS and CPU
- the `.sigstore.json` file came from a different tag
- Sigstore verification fails
